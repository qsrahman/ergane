# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

`muagent` is a minimal interactive terminal chat agent built on the OpenAI **Responses API**. It's a `src`-layout package (`src/muagent/`); see Architecture for the modules.

## Commands

Uses `uv` with Python 3.14 (`.python-version`, `requires-python >= 3.14`).

```bash
uv sync              # install dependencies (including pytest and mcp) into .venv
uv sync --extra mcp  # what a user needs for MCP servers; `mcp` is an optional extra
uv run muagent      # start the REPL; same as `uv run python -m muagent`
uv run pytest        # run the tests
uv run pytest tests/test_repl.py::TestRepl::test_strips_input_and_skips_blank_lines  # single test
uv run ruff check . && uv run ruff format --check .   # lint and format check
uv run pyright src tests   # type check (pyright is a dev dependency)
```

## Tests

- `tests/fake_api.py` is a fake Responses API, and the `fake_server` fixture in `tests/conftest.py` runs it on a local port, using the real SDK client and streaming parser. The most recent user message picks the outcome: `"incomplete"`, `"failed"`, `"empty"` (completed with no output), `"refusal"`, `"cancelled"` (text, but a status other than completed or incomplete), `"truncated"` (a stream with no terminal event), `"tool_call"` (calls a tool until its output is in the input, then replies with text), `"tool_call_reasoning"` (the same, with a reasoning item before each call, as a reasoning model sends), `"tool_call_parallel"` (two calls in one response), `"tool_loop"` (calls a tool every time), `"error_event"` and `"error_event_nocode"` (a stream `error` event, with or without a code, after the first delta, then the stream ends), `"reset"` (the connection is reset after the first event) and `"cut_after_text"` (the stream ends after the first piece of text), `"flaky"`, `"flaky_reset"` and `"tool_call_flaky"` (the stream breaks the first time the same request is sent, as a truncation, a reset, or after the tool's output, and works the second time), `"http_error"` (a 400 response), `"tool_then_X"` (a tool call, then scenario X once the tool's output is in the input, e.g. `"tool_then_failed"`, to fail a round after the first), or anything else for a completed `"Hello world"` reply. Request bodies are recorded in `fake_server.requests`.
- The autouse `isolate_config` fixture runs each test in an empty `tmp_path` that is also `XDG_CONFIG_HOME`, and clears the config environment variables (taken from `Config`'s fields, so a new setting needs no change here), so the developer's own config file and environment do not leak in. `TestLoadConfig` writes its config files into that `tmp_path`, and the default-location tests point `HOME` there too.
- `tests/fake_mcp_server.py` is a stdio MCP server (the SDK's own `MCPServer`) with a tool for each case a client must handle: an annotated and an unannotated tool, one that claims to be read-only, errors, a slow call, one that exits the server, an image, a big result, stderr output, an environment lookup, and two names that collide once cleaned. `test_mcp_client.py` starts it as a subprocess, one shared by the tests that only call it and separate ones for timeouts, Ctrl-C, crashes and start failures; the server's stderr goes to `tmp_path / "mcp.log"`.
- The test files mirror the modules: `test_config.py`, `test_context.py`, `test_agent.py`, `test_commands.py`, `test_repl.py`, `test_console.py`, `test_cli.py`, `test_tools.py`, plus `test_fake_api.py`, which checks the fake's tool scenarios through the real SDK in both modes. Plain helpers (`make_config`, `make_context`, `run_repl`) live in `tests/helpers.py`; the `client` and `make_agent` fixtures are in `conftest.py`.
- Tests build objects directly instead of monkeypatching. `make_config(...)` builds a `Config`, and the `make_agent` fixture builds an `Agent` wired to the fake server (`make_agent(tools=[...], STREAMING=False)`; tools a test defines are made with `Tool.from_function`). `Agent` tests check return values and `TurnError`, not printed output. `TestRepl` replaces `agent.run_turn` on a single instance, and `TestReplRendering` drives a real `Agent` through `run_repl()`.

The package is built with `uv_build`, which expects `src/muagent/__init__.py`. The `muagent` script is `muagent.cli:main` in `[project.scripts]` (`python -m muagent` runs `__main__.py`), and `uv sync` installs the package in editable mode. Tests import the modules directly, for example `from muagent.agent import Agent`.

## Configuration

`load_config()` builds `Config` (pydantic-settings) from, highest priority first: environment variables and the user file `$XDG_CONFIG_HOME/muagent/.env` (default `~/.config/muagent/.env`), which may be missing. A `.env` in the working directory is deliberately not read: whoever controls a project could set `OPENAI_BASE_URL`, and the API key and every prompt would go wherever they chose (`mcp.json` is user-level only for the same reason). Keys that aren't settings are ignored (`extra="ignore"`). Only the `OPENAI_*` settings have an alias; the others are read from the variable named like the field (`max_turns` from `MAX_TURNS`, in any case), and `main()` shows a bad one in upper case.

| Variable | Default | Notes |
|---|---|---|
| `OPENAI_API_KEY` | — | required; kept as a `SecretStr`, so printing the config doesn't reveal it |
| `OPENAI_BASE_URL` | `None` | for OpenAI-compatible endpoints |
| `OPENAI_MODEL` | `gpt-5.4-mini` | |
| `STREAMING` | `true` | stream deltas vs. single `responses.create` |
| `MAX_CONTEXT_TOKENS` | `65536` | budget for the whole request input: instructions, tool definitions and history; excludes the output |
| `REASONING_EFFORT` | unset | SDK `ReasoningEffort`; unset sends no `reasoning`, since non-reasoning models reject it |
| `MAX_TURNS` | `25` | most model calls per prompt: the cap on the tool loop |

`Config` itself only validates and raises `ValidationError`. `main()` prints the per-field errors and exits with status 1.

MCP servers are not settings: they are listed in `$XDG_CONFIG_HOME/muagent/mcp.json` (default `~/.config/muagent/mcp.json`), `{"mcpServers": {name: {type, enable, command, args, env, url, headers, read_only, tools, startup_timeout, call_timeout}}}`, read by `load_servers()` in `mcp_client.py`. A missing file means no servers; a mistake in it (not JSON, an unknown key, a bad name, no command) is a `ValidationError` that `main()` reports with the file's path and exits with status 1, the names as written (not upper case: they are not variables). Only the user-level file is read, never one in the working directory, because a server is a program that runs when muagent starts and a project must not be able to start programs. Each server's stderr goes to `$XDG_STATE_HOME/muagent/NAME.log` (default `~/.local/state/muagent/`), emptied at each start. `config.py` has `user_config_dir()` and `user_state_dir()`, with the XDG rules (an unset, empty or relative variable is ignored) in one place.

## Architecture

[TURN.md](TURN.md) walks one turn through these modules, with the request, the outcomes and what the user and the model each see. Keep it in step when the turn flow changes: the rounds and their stops in `Agent.run_turn`, what `_run_tools` shows and sends, what `save_turn` keeps, or a new way for a turn to end.

The modules, in dependency order (each imports only from those above it):

- `tools.py`: the `@tool` decorator and `Tool`.
- `mcp_client.py`: `McpServer`, a connection to an MCP server (a program over stdio, or a url over streamable HTTP) whose tools become `Tool`s. It imports `mcp` only when a server starts.
- `config.py`: `Config` (the settings model), `load_config()` and `EFFORTS`.
- `context.py`: `Context`, the conversation history and how it is trimmed, and `estimate_tokens()`, which the agent's tool loop uses too.
- `agent.py`: `Agent`, `TurnError`, `SYSTEM_PROMPT` and `SYSTEM_PROMPT_NO_TOOLS`.
- `console.py`: `Console`, which owns all terminal output, and `sanitize()`.
- `commands.py`: the `@command` registry and the slash commands. It imports `Repl` for type checking only.
- `repl.py`: `Repl`, the input loop and dispatch.
- `cli.py`: `main()`, which `__main__.py` calls.

`main()` only loads the config and `mcp.json`, reporting errors, starts the MCP servers, and wires the pieces together: `Repl(Agent(config, tools=mcp_tools), COMMANDS).run()`, closing the servers in a `finally`. muagent has no tools of its own: they all come from `mcp.json`, and with none the agent is a plain chat that sends `SYSTEM_PROMPT_NO_TOOLS`. A tool written in Python is added to that list in `main()`. Dependencies are passed in through constructors (`Agent(config, client=None, tools=())`, `Repl(agent, commands)`); there is no global config lookup.

- **`Context`** holds the history (`items`). Every request uses `store=False`, so the full history is resent each turn.
  - `begin_turn(prompt, max_tokens)` returns a copy of the history plus the new user message, trimmed to the budget, without changing `items`. The budget is an argument, not state: `Agent` passes what is left of `config.max_context_tokens` after `_fixed_tokens()` (an estimate of the instructions and the tool definitions, which every request carries) on every call, so every setting is read where it is used and none is copied at startup (except `api_key` and `base_url`, which build the client). The budget is for the whole request, as the mid-turn check below also measures it (the server's `usage.input_tokens` counts the instructions and the tools), so a long tool list leaves less room for the history, and a room that is zero or less trims every turn but the newest.
  - `save_turn(items)` is the only way a turn becomes history. It takes the whole history after the turn (the input `begin_turn()` returned plus everything the model produced), so a turn can hold more than a prompt and a text reply, such as reasoning, function-call and function-call-output items. They stay together: `undo()`, `rewind()` and trimming all work on whole turns, split at `user` messages. `Agent` calls it after a `completed` (or status-less, as some compatible servers send) response with non-empty `output_text`, and also for an `incomplete` response with text, so the partial reply the user saw is kept. Failed or empty responses and exceptions leave history untouched, except after a completed round (see `Agent`), so user and assistant messages always alternate. Preserve this invariant when changing the turn flow.
  - `undo()` drops the last turn (the last `user` message and everything after it) and reports whether there was one.
  - `rewind()` is what `/retry` uses: it drops the last turn if it was saved and returns its prompt. `Context` tracks `last_prompt` (set by `begin_turn()`) and `last_saved` (set by `save_turn()`, cleared by `begin_turn()`, `undo()` and `reset()`), so all history changes and the flag live in one class.
  - Trimming, inside `begin_turn()`, estimates each item's tokens once with `estimate_tokens()` (UTF-8 bytes of its JSON ÷ 4, tokenizer-agnostic; a reasoning item's opaque `encrypted_content` is left out, because the API counts it as the few tokens of reasoning it holds, not its length: 18 tokens for 1,636 characters on gpt-5.5, against about 444 estimated) and drops whole turns from the front, each up to the next `user` message, until under budget. It never drops the most recent user turn, so a single oversized prompt can still exceed the limit.
- **`@tool`** (`tools.py`) turns a plain function into a tool, as in FastMCP. The name is the function's name, the description is its docstring (all of it, so write it for the model), and the parameters come from its type hints and defaults; `Annotated[int, Field(le=200, description="...")]` adds limits and per-parameter descriptions. It returns `str`. Mistakes fail at import: no docstring, a non-`str` return, an unannotated parameter, `*args`/`**kwargs`/positional-only/async. A tool is `read_only` by default; `@tool(read_only=False)` declares one that changes things. `Agent` enforces it: a tool that is not read-only runs only if the user confirms (see `Agent` below). The decorated name is a `Tool`, so call `add.call('{"a": 1}')` in a test. A `Tool` is only what the agent needs: `name`, `description`, `parameters` (the JSON schema), `check` (arguments as JSON text → a problem as text, or `None`, without running the tool), `runner` (arguments as JSON text → the result, may raise) and `read_only`; `Tool.from_function` fills them in from a function, and a tool from anywhere else (an MCP server's) fills in the same parts. For a function, `check` uses a second `TypeAdapter` over a do-nothing copy of the function made with `functools.wraps`, because validating against the function itself calls it. `Tool.call` takes the model's JSON text, checks it the same way (every check words its problem through `invalid_arguments()`, so the model always reads `Invalid arguments: ...`), and never raises: bad JSON, invalid arguments and any exception from the function come back as text (`Invalid arguments: ...`, `Error: Type: message`) for the model to correct, except Ctrl-C. Output over `MAX_OUTPUT_CHARS` is cut with a marker.
- **`McpServer`** (`mcp_client.py`) connects to one MCP server and turns its tools into `Tool`s: `McpServer(name, config, log)` with a `McpServerConfig` (which has exactly one of `command` for stdio and `url` for streamable HTTP, the trust and the timeouts) and a log path that only a command uses (a url has no stderr, so no file is made); a `McpServer` is used once, since its stop and finished events stay set after `close()`, then `start()`, `tools()` and `close()`; `start()` is `launch()` (begin starting, without waiting) then `connect()` (wait until it is up), so that several servers can start at the same time; it opens and empties the log file in `launch()` and closes it in `close()`, and `close()` cancels a server that is still starting, closes the event loop once its thread has ended (or its selector and sockets stay open: three descriptors per server), because one that has not answered cannot be asked to stop, and `start()` says so if the `mcp` package is not installed (it is an optional extra, `muagent[mcp]`, and part of the dev group). `start_servers(configs, log_dir, on_notice, environ=os.environ)` first fills in the `${NAME}` placeholders of each server from `environ` (`_expand`: only in `args`, `env` and `headers`, not in `command` or `url`; one pass, so a value is not searched again; `$NAME` and `${` without a name are plain text; a variable that is not set skips that server with a notice naming the variable and where it is used, never a value, because sending the placeholder as the key would fail in a way that is harder to see), then launches every configured server, then connects to each in turn (so they start at the same time, and the notices come in the order of the file), and returns the running ones and all their tools: a server that fails is reported through `on_notice` and left out, because a server must never stop muagent, and if the start is interrupted (Ctrl-C) the servers already running are closed. The SDK is async and muagent is not, so each server has a daemon thread running its own event loop; one task there (`_serve`) enters and leaves the whole connection, because the SDK's task groups must be left by the task that entered them, and a call is `run_coroutine_threadsafe(...).result(timeout)`. A call that times out is cancelled and the connection stays usable; Ctrl-C cancels the request and re-raises; any other failure of the request (the server has stopped) is a `McpServerError` that names the server, which `Tool.call` turns into text for the model. The task's end is noticed by a done-callback (`_task_done`), not by code in `_serve`, and the callback also reads the task's exception, because a server that dies ends the task with one, the caller already has it as the error of the call that failed, and asyncio would otherwise log it with a traceback to the terminal when the task is collected; because a task cancelled before its first step never runs any of its code; `_close` cancels through a callback run on the loop, after the one that creates the task, for the same reason. `start()` raises `McpServerError` (with the exception inside the SDK's `ExceptionGroup` unwrapped) if the command cannot run, exits first, or does not answer in time, and cancels the task so no process is left; `close()` stops the task (the SDK then stops the server) before the loop and thread. A server in `mcp.json` is a program (`command`, `args`, `env`) or a `url` (with `headers`), never both, `type` (`local` or `remote`) is optional but must agree with which of the two it is, `enable: false` leaves it out of the start without a word, and `McpServerConfig` refuses a url that is not `https://` unless the host is `localhost`, `127.0.0.1` or `::1` (headers and tool calls must not cross a network unencrypted), has no host, or holds a user name or password (they belong in `headers`; a URL ends up in logs); a mistake there is reported like any other in the file. For a url, `_serve` opens an `httpx2.AsyncClient` with the headers and the SDK's timeouts (30 s, and 300 s to read, since a server may hold a response open) and `streamable_http_client` on it, in an `AsyncExitStack` in the one task; the SDK follows redirects only within the url's origin, so the headers go nowhere else. A url server's errors say what failed (`ConnectError`, `MCPError: Not Found`) but never print the url, which may carry a key. A program's server starts in the directory muagent was started in (there is no `cwd` setting: a `cwd` key in `mcp.json` is an unknown key and the file is refused), and it does not inherit this program's environment, only the SDK's short allow-list plus `env`, so it does not see `OPENAI_API_KEY`; its stderr goes to `errlog`, or it would land in the terminal. Tool names are `server__tool` with every character the API rejects (`^[a-zA-Z0-9_-]+$`, at most 128; one bad name fails the whole request) replaced by `_` and a number added to names that then collide; the server name is checked against the same characters. `tools` (optional, not empty) lists the server's own tool names to offer; `tools()` offers only those, and a name the server does not have raises `McpServerError` naming it and the tools it has, so the server is left out with a notice (a typo must not silently offer nothing). Every tool is `read_only=False` unless the caller says `read_only=True` for the whole server: the server's own `readOnlyHint` is never used, since a server can claim anything. `Tool.validator` checks only what cannot work (a JSON object with the required keys) because a JSON Schema check is stricter than servers, which accept `"4"` for an integer; the server validates the rest and its errors come back as `Error: ...` text. A result is the text blocks joined, with a placeholder such as `[image: image/png]` for the others. The tools list is read across all pages, once; changes the server announces later are not followed. `main()` starts them before the REPL (a notice for each one that fails, and a blank line after them if there was one; a server that starts is not announced, its tools are counted in the banner) and closes them after it, even if it fails; Ctrl-C while they start exits with status 130.
- **`Agent`** owns the config, the client and the `Context`, and does no terminal I/O. `run_turn(prompt, on_text, on_notice, confirm)` sends one turn and passes reply text to `on_text`: each delta when streaming, or the whole reply once otherwise (before the status check in both modes, so partial text is always shown). Status messages such as trimming go to `on_notice`. It raises `TurnError` for incomplete, failed, refused or empty responses. `run_turn` only applies the policy: `send_response()` gets the final response (the only place that calls the API), and `_response_status()` turns a response into an error message or `None`. A tool call (no text) is fine; a final response with no text is an error. The reply is saved when there is text and the turn either worked or was cut off (`incomplete`); then the problem, if any, is raised. The request is built once as the SDK's own `ResponseCreateParamsBase` and unpacked into both `create` and `stream`, so pyright checks the keys and they are written once; `reasoning` is added only when `REASONING_EFFORT` is set. `stream()` is kept over `create(stream=True)` because it rebuilds the final output when a compatible server leaves it out of `response.completed`. The system prompt plus environment info (OS, current date) is passed via `instructions`, not stored in the history: the prompt first and the environment last, so the part that never changes can be cached. There are two prompts, `SYSTEM_PROMPT` for an agent with tools and `SYSTEM_PROMPT_NO_TOOLS` for one without, which differ only in the `# Tools` section (see Conventions). When streaming, `send_response()` takes the final response from the terminal stream event, because `get_final_response()` raises on incomplete or failed streams. If the stream ends with no final response, the `TurnError` carries the reason from the server's last `error` event (`Stream error: CODE: MESSAGE`), or says the stream ended without a final response if it sent none. Before that error, `_send_response` sends a round again, up to `STREAM_RETRIES` (2) times, with a notice `REASON; trying again (N of 2)`, when its stream broke in a way a second try can get past (`StreamCut`, a `TurnError`): it ended with no final event and no `error` event, or the connection dropped after the stream began (the SDK raises `APIConnectionError` for that, and only retries a request that fails to start). It does so only while no reply text has reached `on_text`, because a second try would show the reply twice, and never for a stream the server ended with an `error` event, which says why and would say it again. Tools run only after a complete response, so a retry repeats a request and never an action. The reason it exists: Ollama's cloud proxy lost its connection to the cloud 100 seconds into a request (`cloud proxy response copy failed` in `~/.ollama/logs/server.log`; one request in 3,776), the stream ended cleanly with no final event, and a turn of 25 rounds of reading was thrown away.
  - Tools: `Agent(config, client, tools)` is given the tools to offer and needs distinct tool names (`ValueError` otherwise); `cli.py` lists the tools to offer. There is no global registry: `@tool` only builds the `Tool`. `run_turn` is a loop of at most `max_turns` model calls: `send_response()` gets a response, and if it calls tools the model's own items (reasoning included) are kept in the turn's working list, `_run_tools()` answers every call, and the model is called again. It stops at a response with no calls, with a problem, at the cap (the turn is then saved, closed with an assistant note `[Stopped after N model calls without a final answer]`, so the model still knows the question and the work done; every call has its output, so history stays valid), or when the turn's size passes `max_context_tokens` after a round (`_next_request_tokens()`: the `usage.input_tokens` the server reported for the request it just answered, which is exact, plus an estimate of the items added since; all estimated when a compatible server sends no usage) (a `TurnError` each time). The budget check first drops tool results instead of ending the turn: `_drop_outputs` replaces the `function_call_output` of the rounds before the latest, oldest first, with `DROPPED_OUTPUT` until the estimate fits (replacing the item, not editing it, since earlier turns' items are shared with the history), with the notice `Context full: older tool results dropped`; only when the latest round alone is over does it raise, and that saves nothing. A failure after at least one completed round (a response with a problem, a stream that kept breaking after its retries or ended with an `error` event, or any other exception from the API client such as an `openai.APIError`; the first round's failure saves nothing, as before) is saved like the cap, closed with an assistant note `[Stopped after N model calls: REASON]` (N: the rounds that completed; REASON: the `TurnError` message, or the exception's type name), and then raised, so the model still knows the question and the work done, some of which may have had effects, and the user can say "continue"; every call has its output at that point, so the invariants hold. Ctrl-C is kept the same way once a round has run: in a later model call the turn is saved as it stands, and in `_run_tools` (which adds each output to the turn's items as it is done, so the finished ones survive) `_answer_open_calls` first gives every call with no output `The user interrupted this call: it did not finish, or did not run.`, so the history stays valid; the note is `[Stopped after N model calls: interrupted by the user]`. Ctrl-C in the first round's model call saves nothing, as nothing has run. `/retry` after such a turn drops it like any saved turn and starts the prompt over: nothing else bounds how far a turn grows while it runs, and every request resends all of it. Every call gets a `function_call_output`, even a failed, unknown or denied one, as text for the model to read and correct. A call whose arguments `Tool.check` rejects is answered with that text and never reaches `confirm`: asking the user about a call that cannot run is noise. A tool that is not `read_only` runs only if `confirm(tool, arguments)` returns True or `"always"` (which also adds the tool's name to `Agent.always_allowed`, a set kept for the session, so that its later calls run without asking, shown as a line like a read-only tool's; `/tools` lists those as "allowed this session"); the default denies, so a caller that passes nothing can never run one, and a denied call's output is `The user denied this call.` Read-only tools are never confirmed. A call that runs without asking is reported through `on_notice` before it runs, as `name(arguments)` shortened to one line of `NOTICE_CHARS` characters (including a call to an unknown tool and one whose arguments `check` rejects, which are never asked about); a call that is asked about is shown by `confirm`, so it gets no line from `_run_tools`, and a screen with both would show it twice. Results are not shown: they go to the model, whose reply says what it found, and showing every output cluttered the display.
  - The turn is saved whole by `Context.save_turn`: the working list (user message, the model's call items, their outputs) plus the final reply as a plain `{"role": "assistant", "content": text}` message. `Context.save_turn` then keeps the tool work (reasoning, calls and outputs) only for the latest turn, so a follow-up can still refer to what the tools found; in earlier turns only the user and assistant messages stay, because the final reply says what the calls found and the tool work is the bulk of the history. Calls and outputs are dropped together, since the API rejects a call without its output (400) and an output without its call. Server-side compaction (`responses.compact`, or `context_management`) is a possible future step: it works on OpenAI and Ollama, but its items are backend-specific.
- **`Console`** (`console.py`) is the only thing that prints replies and status lines, and it asks the user's permission for tools. `write()` prints text as it is (sanitized), `notice()` prints a bracketed status line, and `blank()`, `end_line()` and `clear()` do what they say. `confirm(tool, arguments)` is the `confirm` callback `Repl.ask()` passes to the agent, and it is one line, one `input()` call: `Allow NAME ARGUMENTS? [y/N/a] `. The line is at most as wide as the terminal (`shutil.get_terminal_size()`, with at least 20 characters for the arguments, whatever the width), because a call with a whole file in it made the line wrap over dozens of rows. The arguments are the parsed JSON on one line, so that whitespace between the tokens cannot push the call off the screen (arguments that are not JSON have their whitespace made one space). If that is too long, `_fit()` cuts every string longer than a cap in the middle, keeping both ends because a long command can be harmless at the start and not at the end, with the longest cap (64, 40, 24, 16, 8) that makes it fit, and failing that cuts the line at its end. Shortening is never silent: the prompt then ends `[y/N/a/?]`, and answering `?` prints the arguments in full (indented JSON, sanitized) and asks again, so the user can always see all of a call before saying yes; the default stays no. `y` or `yes` allows, `a` or `always` returns `"always"` (see `Agent`), and anything else, end of input included, denies. The question is what `input()` is given, not something printed first, and the cursor is marked as mid-line while it waits, so that after Ctrl-C (which cancels the turn) the next notice starts on a fresh line. The `> ` prompt of the input loop stays in `Repl`. Its output is plain text (`write()`, `blank()`, `end_line()`: a streamed reply, a command's output) or a status block (`notice()`, `confirm()`), and both go through one private `_emit()`, which is the only place that separates them: a status block always starts on a fresh line (it tracks `at_line_start`, so a status line never lands in the middle of a reply that was cut off), and plain text that follows a status block starts after a blank line (it tracks `after_status`), so tool-call lines never run into the reply. A new kind of output goes through `_emit()` too. `sanitize()` strips control characters, bidi marks, overrides and isolates, and the invisible tag characters (U+E0000–E007F), since replies and notices carry text from the model or server; it keeps the zero-width joiners that Persian, Urdu and emoji text need. `Console()` sets stdout's error handler to `replace`, so text the terminal's encoding cannot show prints as `?` instead of raising `UnicodeEncodeError` halfway through a reply. `/clear` only prints its escape codes when stdout is a terminal.
- **`Repl`** owns the input loop and dispatch, and prints through `self.console`. It reads with an optional prompt_toolkit `PromptSession` (`Repl(agent, commands, session)`), built by `terminal_session(commands, history_path, *, input=None, output=None)`, which returns `None` unless stdin and stdout are terminals (prompt_toolkit would only warn about redirected input), so the loop falls back to `input("> ")` and the tests, which run without a terminal, need no session; `main()` passes `user_state_dir() / "history"`. The session gives a `FileHistory` (plain text, mode `0600` in a `0700` directory; in memory if the file cannot be made), `_CommandCompleter` (the slash commands, then the `arguments` a `Command` lists, such as `/effort`'s levels: prompt_toolkit's `NestedCompleter` finds the first word with a pattern that does not take `/` as part of it, so it completes no command), `AutoSuggestFromHistory` and bracketed paste, so a pasted block is one prompt (no `readline`: macOS Python uses libedit, which has none). Alt-Enter and Ctrl-J add a line; Shift-Enter does where the terminal sends it as its own key, which `ANSI_SEQUENCES` is taught for kitty's `CSI 13;2 u` and xterm's `CSI 27;2;13 ~` (read as Alt-Enter), but most terminals send a plain Enter for it and must be set to send one of those. `Console` takes an `ask` function that reads the answer to `confirm` (`input()` if omitted); `Repl` gives it a second, history-less `PromptSession` on the same input and output, so the answer has the same line editing without being kept as a prompt or completed as a command. `private_state_dir()` in `config.py` makes `user_state_dir()` `0700` (it holds the history and the server logs) and `main()` uses it for both. `TestTerminalSession` drives a real session through `create_pipe_input()` and `DummyOutput`, which `terminal_session` accepts for that. `run()` starts with a one-line banner, `muagent | model: NAME | effort: LEVEL | N tools | /help lists commands` (without the effort when none is set, and without the tool count when there are none), and a blank line.
  - `handle()` splits input at the first space: the first word picks a command, and the rest (stripped, `""` if none) is passed as `args`. A single word starting with `/` that isn't a command shows "Unknown command" instead of reaching the model. Anything else goes to `ask()`. A handler that raises is shown as `Command error: ...`, and Ctrl-C inside one as `Cancelled`; either way the session continues, so a new command needs no error handling of its own.
  - `ask()` runs one turn (after a blank line under what the user typed), passing `console.write`, `console.notice` and `console.confirm` to the agent, then shows any `TurnError`, an API error as `describe_error()` words it (`API error 429 (insufficient_quota): message. hint`, the usual cause named for 401, 403, 404 and 429, since the SDK's own text ends in a Python dict), any other as `Agent error: ...`, or `Cancelled` as a notice. Ctrl-C cancels just that turn, and the loop continues.
  - Slash commands live in the module-level `COMMANDS` registry in `commands.py` as `Command(handler, description)`; `main()` passes that dict to `Repl(agent, commands)`, which keeps it as `Repl.commands`, matched case-insensitively, and `/help` lists it. A handler is `handler(repl: Repl, args: str) -> str | None`: it returns a short status message, which `handle()` shows as a notice followed by a blank line, or `None` for no message. To add a command, write a handler with a docstring and decorate it with `@command("/name")`: the first line of the docstring is the description `/help` shows, as a tool's docstring is its description. A name must be a slash, then lowercase letters, digits and hyphens, because input is lowercased before the lookup and a leading slash keeps a plain prompt from matching; a bad name, a duplicate or a missing docstring fails at import (`ValueError`). Stack decorators for aliases (`/exit` and `/quit`).
  - `/model` and `/effort` change `repl.agent.config` for the rest of the session, and `/tools` lists `repl.agent.tools` in two groups, those that run without asking and those that ask first; `/effort` validates against the SDK's `ReasoningEffort` (`EFFORTS` lists its values). `/retry` calls `context.rewind()` and resends the prompt it returns.

## Conventions

- The code uses Python 3.14 syntax, such as the unparenthesized `except KeyboardInterrupt, EOFError:` (PEP 758). ruff takes its target from `requires-python`; `[tool.ruff]` only sets `src = ["src", "tests"]` so `muagent` and `fake_api` sort as first-party imports.

- Google-style docstrings (`Args:` / `Returns:` / `Raises:`) on functions.
- Show the user only what they need, to decide or to know that something went wrong. A call that asks is one line, the question; a call that runs freely is one line; a result is not shown (the reply says what it found); a server that starts is not announced (the banner counts its tools); the banner is one line. Before adding output, ask whether anyone would miss it. The layout of an exchange is pinned in `TestReplRendering` in `test_repl.py`, with `input()` standing in the way a terminal looks (prompt, typed line, Enter), so a change that adds a line shows up there.
- Output is a plain terminal: the system prompt forbids LaTeX in favor of Unicode math and says Markdown is not rendered. Keep those constraints if editing the prompt.
- The system prompt follows OpenAI's guidance for agentic coding models (sections for role, tools, how to work and replying; finish the task in the turn; a plain line between asking and assuming; proportionate checks; never revert what you did not change; concise, outcome-first answers), and it depends on how the program behaves: the user sees each tool call but not its result (so the prompt tells the model to say what it found), a denied call comes back as the text `The user denied this call.` (so it tells the model not to repeat it), and tool results are untrusted text (so it tells the model they are data, not instructions; OpenAI's pages give no wording for this, it comes from our own threat model). If one of these changes in the code, change the prompt, and `test_the_prompt_*` in `test_agent.py` will point at the words. The prompt also asks for a scratch script to be written in the system's temporary location, never in the project, and the directory deleted afterwards, also after a failure, and for nothing to be deleted that the model did not create (so it does not name `rm -rf` as forbidden: that is how the scratch directory is removed). That is a request, not a guarantee: muagent tracks no files, and it goes unmet after Ctrl-C (the turn is dropped, so the model forgets), a denied call, or a script that keeps failing. A server started by muagent gets no `TMPDIR` (the SDK passes only a short allow-list of variables), so its temporary location is `/tmp`. The section is in the with-tools prompt only, for the reason above.
- Test a prompt change against the models, not by reading it. A change that looks harmless can break a model: telling gpt-5.5 "never write a tool call out as text" made it do so (right 1 time in 6, and 6 in 6 once the sentence was gone), and a prompt full of tool language made gemma4 return an empty reply when no tools were offered, which is why `SYSTEM_PROMPT_NO_TOOLS` never mentions calls. Compare the old and new prompt on scenarios with a pass/fail check each (uses a tool, says it cannot without one, ignores an instruction hidden in a file and says so, is not repeated after a denial, no LaTeX, no Markdown, reports what a tool found, gives code instead of only asking), several runs each, on the models you use. The wording of a rule can be misread: "a new temporary directory" alone made gemma4 create `temp_x/` in the project, and naming the system's temporary location ("for example with `mktemp -d`") took scratch-script cleanup from 0 to 8 of 8. Test a rule that touches files with a simulated shell, which records the commands and returns canned output, so that nothing a model writes is run, and give it realistic answers: one that replied to everything with just an exit code made gemma4 repeat `git status` for 25 calls, which looked like a regression of the prompt and was the harness. Check what a rule leaves undone as well (no script for arithmetic, nothing deleted that the model did not make, no `git reset --hard` unasked).
